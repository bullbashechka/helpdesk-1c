## Definition of Done

- Приложение запускается локально как клиент-серверная система React → REST API → SQLite.
- Все семь таблиц из PRD созданы, связи и внешние ключи работают.
- При первом запуске создаются фиксированные статусы, категории и демонстрационные данные.

- Пользователь может управлять клиентами, договорами и сотрудниками.
- Дашборд показывает счётчики, графики по статусам и категориям, список последних заявок.
- Отчёты за период и часы по сотрудникам формируются и экспортируются в CSV.
- Удаление связанных записей блокируется понятным сообщением.
- Авторизация, роли и редактирование статусов/категорий не реализованы, как указано в PRD.

# Модуль «Вопросы с WhatsApp» — план реализации (этап 1)

Источник: [PRD-whatsapp.md](PRD-whatsapp.md). Структура повторяет чек-лист Bitrix24 **#8156 «Этап 1»** (5 пунктов) — каждый пункт ниже = один чекбокс из Bitrix, под ним инженерные подзадачи «как делаем».

Скоуп этапа 1: один номер, режим **чтения** (без автоответов), ручной триаж, локальная разработка. Всё помеченное **«Потом»** — см. одноимённый раздел.

## Этап 1 (Bitrix #8156)

### 1. Коннектор к WhatsApp — 1 номер по QR, режим чтения, локально

- [x] Отдельный процесс на `whatsapp-web.js` (Puppeteer/Chromium), однократная авторизация по QR-коду, сохранение сессии. (https://github.com/bullbashechka/whatsapp-web.js)
- [x] Конфигурация коннектора: токен для backend, URL backend, один рабочий номер; без автоответов и отправки сообщений (только чтение).
- [ ] Тестовый прогон на некритичном номере (риск блокировки за автоматизацию).

### 2. Получать все новые входящие сообщения от клиентов и сохранять в базу

- [x] Схема БД: `wa_messages` (номер отправителя, имя из WhatsApp, ссылка на клиента, текст, дата/время, статус обработки, ссылка на номер-приёмник, ID сообщения WhatsApp), справочник статусов обработки (новое / в работе / создана задача / архив-мусор), таблица номеров-приёмников `wa_receivers` (на этапе 1 — одна запись); внесение в `SCHEMA_SQL` (`db/bootstrap.js`), пересев демо-базы.
- [x] Внутренний `POST /api/whatsapp/ingest`, защищённый общим токеном из конфигурации (`config/env.js`); валидация полезной нагрузки.
- [x] Коннектор подписывается только на **новые входящие** (история до подключения не выгружается) и шлёт их в `ingest`.
- [x] Дедупликация по ID сообщения WhatsApp — повторная доставка (после переподключения) не создаёт дубликат.
- [x] Привязка к клиенту по телефону: нормализация обоих номеров (убрать `+`, пробелы, скобки, дефисы; из `7707...@c.us` взять цифры), сравнение нормализованных строк (при необходимости — по последним N цифрам `8`/`+7`); не найдено — сообщение без привязки.

### 3. Сохранять вложения (фото и файлы) с возможностью просмотра

- [x] Схема: `wa_attachments` (ссылка на сообщение, тип фото/документ, имя файла, путь на сервере); голосовые на этапе 1 фиксируются как плейсхолдер без файла.
- [x] Приём и сохранение фото/файлов на сервере при ingest, запись метаданных.
- [x] Endpoint просмотра/скачивания вложений; компонент просмотра готов. Размещение в списке инбокса и вёрстка карточки сообщения/задачи остаются в пунктах 4/5.

### 4. Пункт сайдбара «Вопросы с WhatsApp»

- [x] Новый пункт навигации и страница раздела.
- [x] Таблица инбокса: отправитель (имя/номер), клиент (если распознан), фрагмент текста, дата/время, наличие вложений, статус обработки.
- [x] Обновление списка через периодический polling REST API (realtime-канал — «Потом»); API инбокса с фильтром активный/архив.

### 5. Ручное управление: открыть сообщение → создать задачу или в архив (мусор)

- [x] Схема: `wa_tasks` (тема, описание, приоритет, статус, ссылка на клиента, ссылка на исходное сообщение, дата создания/обновления) и фиксированные статусы задач (новая / в работе / выполнена / закрыта).
- [x] Карточка сообщения: полный текст, вложения, распознанный клиент (иначе имя+номер из WhatsApp), статус и дата/время.
- [x] «Создать задачу» — форма с предзаполнением (текст → описание, клиент → если распознан), обязательны тема и приоритет; связь сообщение→задача один-к-одному; статус сообщения → «создана задача». _(В дальнейшем — авто-создание задачи в Б24, см. «Потом».)_
- [x] «В архив (мусор)» — обратимо: фильтр/вкладка архива и действие «вернуть в инбокс» (статус → «новое»).
- [x] Отдельный список задач WhatsApp (самостоятельная сущность, не смешивается с «Заявками») с фильтрами по статусам, редактированием темы/описания/приоритета/статуса и доступом к исходному сообщению с вложениями.

### Проверка готовности этапа 1

- [x] Smoke-тесты API: ingest 201/200, дедупликация, валидация payload, статус коннектора, нормализация и привязка к клиенту по телефону (`backend/test/whatsapp.smoke.test.js`); unit-тесты фильтрации сообщений и очереди (`connector/test/`).
- [x] Smoke-тесты API: создание задачи, запрет дубля, архив/возврат, список/счётчики задач, получение задачи с исходным сообщением, обновление задачи.
- [ ] Ручной прогон сценария: входящее → инбокс → задача / архив.

## Потом (Bitrix #8156)

Не входит в этап 1, зафиксировано как план:

- [ ] **Деплой коннектора на VPS (24/7)** — автозапуск, мониторинг сессии.
- [ ] **ИИ** — авто-распознавание реального вопроса, отсев мусора, авто-создание задач, оценка важности.
- [ ] **Второй номер** (АУП / ЦС) — разделение потоков по источнику.
- [ ] **Интеграция с Bitrix24** — выгрузка задач в проект (например, «Вопросы с WhatsApp»).
- [ ] **Голосовые сообщения** + расшифровка речи.
- [ ] **Создание отчётов** для отчётности (в т.ч. экспорт в CSV входящих/задач).

> Прочее из PRD, не вошедшее в чек-лист Bitrix: официальный **WhatsApp Business API** (замена `whatsapp-web.js` при критичном риске блокировки); поля исполнителя/категории/дедлайна у задач; несколько телефонов на клиента; объединение сообщений в одну задачу; realtime-канал (WebSocket/SSE) и полноценная аутентификация коннектора.

# Автокатегоризация WhatsApp-сообщений — план реализации

Источник: [docs/superpowers/specs/2026-06-25-wa-categorization-design.md](docs/superpowers/specs/2026-06-25-wa-categorization-design.md).

Цель: автоматически отделять обращения-заявки от остального потока в WhatsApp-инбоксе. Сообщения с пометкой «проблема»/`#проблема` относятся к категории «Проблема», остальные — к «Прочее». Автоопределение — подсказка, финальное решение за оператором. Коды категорий в API: `problem` / `other`; русские подписи живут в конфигурации и на фронте.

## Этап 1. Конфигурация категорий и распознавание

Цель: вынести категории и ключевые стемы в конфигурацию и реализовать чистую функцию распознавания (Фича 3, ядро Фичи 2).

- [x] Конфигурационный файл категорий: упорядоченный список категорий, для каждой — код, русская подпись, набор стемов. «Прочее» (`other`) — служебная категория по умолчанию без стемов. «Проблема» (`problem`) — единственный стем `проблем`.
- [x] Функция распознавания категории по тексту сообщения: нижний регистр, разбивка на слова, снятие ведущей `#`, сравнение по префиксу-стему. Первая подходящая категория по порядку конфигурации; нет совпадений или нет текста → `other`.
- [x] Хелперы конфигурации: список допустимых кодов категорий и проверка кода на валидность (для API и фильтров).

Зависимости: нет.

## Этап 2. Модель данных и миграции

Цель: добавить поля категории и источника её определения в `wa_messages` так, чтобы работало и на свежей, и на существующей базе (Фича 1, схема из Фичи 7).

- [x] В `SCHEMA_SQL` (`db/bootstrap.js`): колонка категории сообщения `NOT NULL DEFAULT 'other'` и колонка источника определения `NOT NULL DEFAULT 'auto'` (значения `auto` / `manual`). Имена развязаны с категориями тикетов (`categories`).
- [x] Идемпотентная миграция в `COLUMN_MIGRATIONS`: дотягивание недостающих колонок через `ALTER TABLE ADD COLUMN` с безопасными `DEFAULT`, без reseed и потери данных.

Зависимости: этап 1 (имена/коды категорий).

## Этап 3. Автокатегоризация на приёме и пересчёт при старте

Цель: проставлять категорию при приёме сообщения и поддерживать её актуальность при смене конфигурации (Фича 2).

- [x] На `POST /api/whatsapp/ingest`: вычислять категорию по тексту, сохранять её и источник `auto` в записи сообщения. Сообщения без текста → `other`.
- [x] Пересчёт авто-категории при старте приложения: для сообщений с источником `auto` категория переоценивается по актуальной конфигурации; сообщения с источником `manual` не трогаются.

Зависимости: этапы 1 и 2.

## Этап 4. API: фильтр, счётчики, переназначение

Цель: расширить API списка/сводки категорией и добавить ручное переназначение (Фича 4 и Фича 5).

- [ ] Список сообщений: фильтр по категории, комбинируемый с фильтром по статусу; неизвестный код категории игнорируется (показываются все), по аналогии со статусом. В каждой записи выдачи — категория и источник определения.
- [ ] Сводка по сообщениям: счётчики по категориям (`problem`, `other`, общее) рядом с существующими счётчиками по статусам.
- [ ] Действие ручного переназначения категории по id сообщения: валидация кода по конфигурации (недопустимый → понятная ошибка на русском), источник → `manual`, доступно при любом статусе обработки.

Зависимости: этапы 1–3.

## Этап 5. Фронтенд: фильтр, бейдж, drawer

Цель: дать оператору фильтр по категории, визуальное выделение заявок и ручное переназначение (Фича 6).

- [ ] Ряд фильтра по категории над вкладками статусов: «Все», «Проблема», «Прочее» со счётчиками; работает совместно с фильтром по статусу.
- [ ] Бейдж «Проблема» на карточке сообщения в таблице инбокса; «Прочее» — без бейджа, нейтральное оформление.
- [ ] В drawer просмотра сообщения — выпадающий список «Категория» для ручного переназначения; после смены обновляются список и счётчики. Все подписи и ошибки — на русском, в стиле раздела.

Зависимости: этап 4.

## Этап 6. Демо-данные

Цель: показать фичу без подключённого коннектора (демо-часть Фичи 7).

- [ ] В демо-данных проставить категории согласованно с распознаванием: сообщения со словом «проблема» — `problem`/`auto`, остальные — `other`. В инбоксе сразу видны и «Проблема» (в т. ч. со статусом «Новое»), и «Прочее». Reseed через `npm run seed:demo`.

Зависимости: этапы 1–3.

## Этап 7. Тестирование

Цель: покрыть распознавание, пересчёт и API (раздел «Тестирование» ТЗ).

- [ ] Юнит-тесты распознавания: падежи «проблема», хэштег-форма, регистр, отсутствие текста (только вложение), пограничное «проблематично» → `problem`, обычное сообщение без пометки, отсутствие ложного срабатывания на вхождение букв внутри другого слова.
- [ ] Юнит-тест пересчёта при старте: `auto`-сообщения обновляются после смены конфигурации, `manual` — сохраняют категорию.
- [ ] Smoke-тесты API: фильтр по категории (в т. ч. в комбинации со статусом), счётчики категорий в сводке, ручное переназначение и отказ при недопустимом коде, игнорирование неизвестного кода в фильтре.

Зависимости: соответствующие этапы реализации.

## Definition of Done (автокатегоризация)

- У каждого WhatsApp-сообщения есть категория (`problem`/`other`) и источник определения (`auto`/`manual`).
- Категории и стемы вынесены в конфигурационный файл; расширение — правкой только этого файла.
- При приёме категория проставляется автоматически; при смене конфигурации `auto`-сообщения пересчитываются при старте, `manual` — нет.
- API списка фильтруется по категории (комбинируемо со статусом), сводка отдаёт счётчики категорий, есть ручное переназначение с валидацией.
- В инбоксе работает ряд фильтра по категории со счётчиками, бейдж «Проблема» и переназначение из drawer.
- Демо-данные показывают обе категории без коннектора; новые поля имеют `DEFAULT` и доезжают на существующую базу без reseed.
- Юнит- и smoke-тесты на распознавание, пересчёт и API зелёные.
