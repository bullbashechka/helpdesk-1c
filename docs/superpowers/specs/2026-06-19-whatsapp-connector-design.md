# Дизайн: Коннектор к WhatsApp (этап 1, Bitrix #8156, пункт 1)

Дата: 2026-06-19
Источник: [PRD-whatsapp.md](../../../PRD-whatsapp.md), [TASKS.md](../../../TASKS.md) — «## Этап 1 (Bitrix #8156) → 1. Коннектор к WhatsApp».

## Скоуп

Только **пункт 1** чек-листа: коннектор к WhatsApp — один номер, авторизация по QR, **режим чтения** (без отправки и автоответов), локальный запуск для отладки.

В скоуп **входит**: отдельный процесс на `whatsapp-web.js`, авторизация и хранение сессии, фильтрация входящих, надёжная доставка в backend, отдача статуса/QR/heartbeat, конфигурация.

В скоуп **не входит** (отдельные пункты этапа 1): схема БД и эндпоинт `ingest` на стороне backend (пункт 2 — описаны здесь только как контракт), вложения (пункт 3), UI инбокса (пункт 4), задачи (пункт 5). Деплой на VPS, прокси, второй номер, WhatsApp Business API — **ПОЗЖЕ**.

## Архитектура

Коннектор — **отдельный long-running процесс** (Node + `whatsapp-web.js` поверх Puppeteer/Chromium), запускается локально рядом с backend. Не имеет прямого доступа к SQLite — общается с backend только по HTTP.

```
WhatsApp Web  ──events──►  Коннектор (процесс)  ──HTTP──►  Backend (Express) ──► SQLite
                            │  - слушает входящие
                            │  - фильтрует
                            │  - дисковая очередь
                            │  - ретрай доставки
                            │  - heartbeat + QR/статус
```

Три внутренние обязанности коннектора:
1. **Приём и фильтрация** входящих сообщений WhatsApp.
2. **Надёжная доставка** в backend через локальную дисковую очередь с ретраем.
3. **Отдача состояния** (живость, состояние сессии, QR-код) в backend для индикатора в UI.

## Принятые решения по эдж-кейсам

### 1. Обрыв сессии и повторный QR
Сессия WhatsApp периодически рвётся (телефон офлайн, разлогин, протухание). Решение:
- Коннектор отдаёт backend своё **состояние сессии** и, когда требуется вход, **картинку QR-кода**.
- Статус и QR показываются **в разделе «Вопросы с WhatsApp»** — оператор видит проблему там же, где работает, и может пересканировать без доступа к терминалу.
- Состояния сессии: `qr_required` (ждём скан), `authenticated`/`ready` (подключено), `disconnected` (отвалилось).

### 2. Backend недоступен в момент приёма — не терять сообщения
Коннектор и backend — независимые процессы; backend может быть недоступен (не запущен, перезапуск, падение). Решение:
- Принятое сообщение сначала кладётся в **локальную дисковую очередь** (переживает перезапуск коннектора).
- Доставка в `ingest` идёт с **повторами** до подтверждения приёма; элемент удаляется из очереди только после успешного ответа backend.
- Защита от дублей при ретрае — **дедупликация по `wa_message_id`** на стороне backend (пункт 2 плана).

### 3. Фильтрация потока
`whatsapp-web.js` отдаёт события на все сообщения. Решение по охвату — **максимальный**:
- **Берём**: личные входящие 1-на-1 **и** сообщения из групп, где состоит рабочий номер; от **любых** номеров, включая отсутствующие в справочнике клиентов (триаж вручную в инбоксе).
- **Отсекаем всегда**: исходящие с самого рабочего номера (`fromMe`), статусы/сторис и рассылки (`status@broadcast`), системные служебные события.
- **Нюанс групп**: в группе «отправитель» — это конкретный участник (`author`), а не сама группа. Для привязки к клиенту используется номер участника; группа сохраняется как источник/контекст.

### 4. Граница «нового»
Правило PRD: история до подключения не выгружается. Уточнение границы:
- Тянем сообщения **новее момента первой авторизации** коннектора.
- **Пропущенное за офлайн добираем**: при возврате после простоя берём непрочитанное, пришедшее за время офлайна (оно новее границы) — согласуется с «нельзя терять».
- Древняя история (старше границы) не тянется. Дедуп по `wa_message_id` исключает повторы.

### 5. Живость коннектора (heartbeat)
Нужно отличать «коннектор работает» от «процесс умер». Решение:
- Коннектор периодически шлёт backend **heartbeat** с текущим состоянием сессии и временем.
- Если heartbeat нет дольше порога — индикатор в UI переходит в «не на связи».
- На этапе 1 — **пассивный индикатор** (онлайн / нужен QR / не на связи + время последней активности). Внешние уведомления (email/мессенджер) — ПОЗЖЕ (этап деплоя).

### 6. Правки и удаления сообщений у клиента
Инбокс — журнал обращений, а не зеркало переписки. Решение:
- Храним принятое сообщение **как есть**; редактирование/удаление сообщения клиентом в WhatsApp задним числом инбокс **не меняет** и не отслеживается.

## Контракт «коннектор → backend»

HTTP, защищён общим токеном из конфигурации (заголовок, напр. `X-Connector-Token`). Эндпоинты на стороне backend (детально — пункт 2 плана):

- `POST /api/whatsapp/ingest` — одно входящее сообщение: `wa_message_id`, номер отправителя (для групп — номер участника), имя из WhatsApp (`pushname`), текст, дата/время сообщения, идентификатор номера-приёмника (`wa_receiver`), признак/контекст группы, метаданные вложений (тело вложений — пункт 3). Идемпотентен по `wa_message_id`.
- `POST /api/whatsapp/status` — состояние сессии + heartbeat + текущий QR (когда `qr_required`). Может быть объединён с heartbeat в один эндпоинт (инженерная деталь плана).

Коннектор считает доставку успешной только при `2xx`; иначе оставляет элемент в очереди и повторяет.

## Конфигурация коннектора

Отдельный `.env` коннектора (по образцу `config/env.js` backend):
- токен для backend;
- URL backend;
- рабочий номер / идентификатор `wa_receiver` (на этапе 1 — один);
- путь к каталогу сессии (`LocalAuth`);
- путь к каталогу дисковой очереди;
- интервалы heartbeat и ретрая.

Без параметров отправки сообщений — режим строго на чтение.

## Тестовый прогон

Первый запуск — на **некритичном номере** (риск блокировки за автоматизацию). Проверяем: авторизацию по QR и переживание перезапуска (сессия сохранена); приём личного и группового входящего; фильтрацию исходящих/статусов; доставку в `ingest` при недоступном и затем поднятом backend (буфер + ретрай, без дублей); корректный статус/QR/heartbeat в backend.

## Открытые инженерные детали (решаются в плане, не продуктовые)

- Объединять ли `status` и `heartbeat` в один эндпоинт.
- Формат и библиотека дисковой очереди (файлы JSON на диске против встроенной мини-БД).
- Точные интервалы heartbeat/ретрая и порог «не на связи».
- Способ локального запуска процесса (npm-скрипт коннектора).
