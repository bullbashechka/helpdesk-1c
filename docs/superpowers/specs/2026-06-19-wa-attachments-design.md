# Дизайн: вложения WhatsApp (фото / видео / документы)

Дата: 2026-06-19
Задача: TASKS.md → «Этап 1 (Bitrix #8156) → 3. Сохранять вложения (фото и файлы) с возможностью просмотра»
Источник требований: [PRD-whatsapp.md](../../../PRD-whatsapp.md)

## Цель

Сохранять фото, видео и документы из входящих сообщений WhatsApp на сервере и
давать оператору просматривать/скачивать их в карточке сообщения и задачи.
Голосовые сообщения как звук не сохраняются (по PRD), но факт их прихода
фиксируется, чтобы реальный вопрос клиента не терялся.

## Решённые продуктовые правила

| Эдж-кейс | Решение |
|---|---|
| Какие типы ловим | фото, видео, документы. Стикеры / GIF / аудиофайлы — пропускаем как шум |
| Файл > 25 МБ | сообщение сохраняется, файл — нет; пометка «слишком большой — открыть в WhatsApp» |
| Скачать с телефона не удалось | сообщение видно в инбоксе; пометка «вложение недоступно, попросите клиента переслать» |
| Сообщение только из голосового | строка-плейсхолдер «голосовое сообщение (прослушать в WhatsApp)»; сам звук не храним |
| Сообщение только из стикера / GIF / аудиофайла | строки в инбоксе нет |
| Медиа без подписи | строка есть, текст пустой, в ней превью/файл |
| Просмотр | фото — превью с увеличением по клику; видео — встроенный плеер; документ — имя + размер + скачать |

Примечание про PRD: правило «голосовые не сохраняются» соблюдено — мы не сохраняем
аудиоданные, только отметку о факте сообщения.

## Транспорт коннектор → бэк

Бинарь едет как **base64 внутри того же JSON-payload**, что и сейчас текстовое
сообщение. Альтернативы (отдельная multipart-загрузка, общий диск) отклонены:

- сохраняется модель «одно сообщение = один POST», поэтому существующие
  дедупликация и повторная доставка после переподключения работают без переделки;
- не нужен общий диск между коннектором и бэком (коннектор позже уедет на VPS — PRD);
- бэк сохраняет файл и строку в БД атомарно, без «полусостояний».

Расплата — лимит размера (см. правила) и разовый пик памяти при флаше очереди
(см. «Известные ограничения»).

## Компоненты и поток данных

```
WhatsApp
  → connector/wa-client.js   (async message handler: тип → kind, downloadMedia с повторами, лимит 25 МБ)
  → connector/queue.js       (без изменений: payload + attachments[] как JSON-файл)
  → connector/sender.js      (без изменений: POST /api/whatsapp/ingest)
  → backend ingest           (лимит тела ↑, декод base64, запись файла, строки wa_attachments)
  → SQLite (wa_messages + wa_attachments) + backend/data/wa-attachments/<id>-<i>.<ext>
  → GET /api/whatsapp/attachments/:id  (отдача с верным Content-Type)
  → frontend AttachmentList  (превью / плеер / скачать)
```

### 1. Данные — таблица `wa_attachments`

Добавляется в `SCHEMA_SQL` (`backend/src/db/bootstrap.js`). Изменение схемы →
требуется пересев демо-базы (`npm run seed:demo`). Демо-вложения не добавляем:
демо-инбокс сейчас не сеется.

Поля:

- `id` — PK.
- `message_id` — FK на `wa_messages(id)`, `ON UPDATE CASCADE ON DELETE RESTRICT`
  (конвенция проекта; удаления сообщений на этапе 1 нет).
- `kind` — `CHECK IN ('photo','video','document','voice')`.
- `availability` — `CHECK IN ('stored','too_large','failed','not_stored')`.
  Для `voice` всегда `not_stored`.
- `original_name` — имя файла как прислал клиент (для отображения и имени при скачивании); может быть NULL.
- `mime_type` — MIME из WhatsApp; может быть NULL.
- `size_bytes` — размер исходного файла, если известен; может быть NULL.
- `stored_path` — путь к файлу **относительно** папки хранилища; NULL, когда файла нет
  (`too_large`, `failed`, `not_stored`).
- `created_at` — `datetime('now')`.

Связь сообщение → вложения: один-ко-многим (схема общая), хотя на практике
whatsapp-web.js доставляет одно медиа на сообщение.

### 2. Коннектор (`connector/src/wa-client.js`)

Обработчик `message` становится `async`. После существующих фильтров:

- Определяем kind по `msg.type` (чистая функция, выносится в отдельный модуль для тестов):
  - `image` → `photo`
  - `video` и **не** `msg._data?.isGif` → `video`
  - `document` → `document`
  - `ptt` → `voice` (плейсхолдер, без скачивания)
  - `sticker`, `audio`, либо `video` с `isGif` → **пропуск** (медиа не добавляем)
- Для `photo` / `video` / `document`: `await msg.downloadMedia()` с 2 повторами при
  ошибке/`undefined`:
  - успех и размер ≤ 25 МБ → `availability='stored'`, `data_base64` в payload,
    `original_name`/`mime_type`/`size_bytes` заполнены;
  - размер > 25 МБ → `availability='too_large'`, без данных;
  - все попытки неудачны → `availability='failed'`, без данных.
- Для `voice` → `availability='not_stored'`, без данных.
- Если поддерживаемого медиа нет и текста нет (стикер/GIF/аудиофайл) → сообщение
  **не enqueue-им** (строки в инбоксе не будет). Если есть текст — обычное текстовое сообщение.

Подпись к медиа уже кладётся в существующее поле `body` (`msg.body`). Очередь и
sender не меняются.

Payload расширяется полем:

```jsonc
"attachments": [
  { "kind": "photo", "availability": "stored",
    "original_name": "screenshot.png", "mime_type": "image/png",
    "size_bytes": 20480, "data_base64": "<...>" }
]
```

### 3. Приём на бэке (`backend/src/app.js`, `services/whatsapp.service.js`, `routes/whatsapp.routes.js`)

- В `app.js` поднять лимит тела `express.json({ limit: '35mb' })` (25 МБ × ~1.33
  для base64 + запас). Дефолтные 100 КБ иначе дадут 413 на любом файле.
- `ingestMessage`: после вставки сообщения обработать `payload.attachments`:
  - **Идемпотентность**: вложения пишем только при свежей вставке сообщения
    (`deduplicated === false`). Повторная доставка файлы не переписывает.
  - Для каждого вложения создаём строку `wa_attachments`. Для `availability='stored'`
    с `data_base64`: декодируем, пишем файл в папку хранилища, имя **генерируем сами**
    — `<message_id>-<index>.<ext>`, где `ext` берём из `mime_type`/`original_name` и
    санитизируем. Клиентское имя сохраняем только в `original_name`. Это закрывает
    path traversal и коллизии.
  - Сбой записи файла (например, нет места) → строка с `availability='failed'`,
    обработку остальных вложений продолжаем.
- Папка хранилища: `backend/data/wa-attachments/`, из конфига
  (`WA_ATTACHMENTS_DIR`, дефолт `./data/wa-attachments`, резолв относительно рабочей
  папки backend, как у `SQLITE_DB_PATH`). Добавить в `.gitignore`.

### 4. Отдача файла — `GET /api/whatsapp/attachments/:id`

- Находим строку по `id`. Если `availability !== 'stored'` или файла нет → 404.
- Отдаём файл с `Content-Type = mime_type`, `Content-Disposition: inline; filename="<original_name>"`.
  Параметр `?download=1` → `Content-Disposition: attachment` (кнопка «Скачать»).
- Путь к файлу берём **только из БД по id** и проверяем, что разрешённый абсолютный
  путь лежит внутри папки хранилища (defense in depth против обхода каталога).
- Без авторизации — консистентно со всем API этапа 1 (PRD: аутентификации нет).

### 5. Read-модель сообщения и фронтовый компонент

Карточка сообщения (задача 4-сайдбар / 5-задачи) и список инбокса ещё не построены.
Чтобы задача 3 была законченной и тестируемой, она поставляет:

- `attachments` в read-модели сообщения: при необходимости минимальный
  `GET /api/whatsapp/messages/:id`, возвращающий сообщение + массив вложений
  (`id, kind, availability, original_name, mime_type, size_bytes`);
- переиспользуемый фронтовый компонент `AttachmentList` (фото — превью с увеличением
  по клику; видео — `<video>`-плеер; документ — имя + размер + «Скачать»; пометки для
  `too_large` / `failed` / `voice`). Все строки UI на русском.

Размещение иконки-скрепки с количеством в списке инбокса и вёрстка самой карточки
остаются задачами 4/5 — они вставляют `AttachmentList` и потребляют read-модель.

## Обработка ошибок (сводка)

| Ситуация | Поведение |
|---|---|
| Файл > 25 МБ | строка `too_large`, файла нет, сообщение сохранено |
| `downloadMedia` падает после повторов | строка `failed`, файла нет, сообщение сохранено |
| Сбой записи файла на бэке | строка `failed`, остальные вложения обрабатываются |
| Повторная доставка (дедуп) | вложения не дублируются и не переписываются |
| Запрос файла по битому id / не `stored` | 404 |
| Тело запроса больше лимита | 413 (лимит выставлен с запасом под 25 МБ) |

## Тестирование

- **Коннектор (unit, без Puppeteer, паттерн `connector/test/`)**: маппинг
  `msg.type` → kind/skip (image/video/gif/document/ptt/audio/sticker); ветка лимита
  25 МБ → `too_large`; ветка неудачного скачивания → `failed`. Логику вынести в
  чистый модуль.
- **Бэк (smoke, паттерн `backend/test/whatsapp.smoke.test.js`)**: ingest с маленьким
  PNG в base64 → 201, файл записан, строка `stored`; `GET attachments/:id` → байты +
  верный `Content-Type`; `too_large` → строка без файла; дедуп не плодит вложения;
  voice → плейсхолдер без файла; битый id и попытка traversal → 404.

## Известные ограничения (намеренно не чиним сейчас, YAGNI)

- Файловая очередь коннектора (`queue.js`) читает весь payload в память при каждом
  флаше; с base64-видео это разовый пик памяти. На объёмах этапа 1 (один номер,
  локально) приемлемо. Если поток вырастет — выносим медиа в отдельные файлы очереди.
