# 004. Клиентский каркас, навигация и API-клиент

## Этап

Этап 3. Клиентская основа

## Цель

Собрать основу frontend: маршруты, навигацию, общий API-клиент, состояния загрузки и ошибок.

## Контекст из PRD

Приложение является единым рабочим местом менеджера/диспетчера. Основные разделы: дашборд, заявки, справочники, отчёты.

## Scope

- Настроить маршрутизацию frontend.
- Добавить основные разделы: дашборд, заявки, клиенты, договоры, сотрудники, отчёты.
- Создать общий API-клиент для REST backend.
- Добавить базовые компоненты таблиц, форм, модальных окон или страниц редактирования по выбранному UI-подходу.
- Реализовать состояния загрузки, пустых списков и ошибок API.
- Добавить единый формат отображения дат, дедлайнов и числовых часов.

## Out of Scope

- Полная бизнес-логика отдельных экранов.
- Графики и отчёты.
- Авторизация.

## Requirements

- Интерфейс не должен показывать элементы входа, регистрации или управления пользователями.
- Навигация должна позволять быстро перейти к основным рабочим разделам.
- Ошибки backend должны отображаться понятным текстом, особенно ошибки удаления связанных записей.
- Формы должны поддерживать клиентскую валидацию обязательных полей, но backend остаётся источником истины.

## Acceptance Criteria

- Пользователь видит навигацию по всем разделам MVP.
- Переходы между разделами работают без перезагрузки страницы.
- API-клиент корректно обрабатывает успешные ответы и ошибки JSON.
- Для недоступного API отображается понятное сообщение, а приложение не падает.
- Пустые списки отображаются как штатное состояние.

- [001. Каркас приложения и окружение](001-project-scaffold.md)
- [003. REST API для справочников и заявок](003-rest-api-core.md) для полной интеграции.

## Implementation Notes

UI должен быть рабочим инструментом, а не лендингом: плотные таблицы, понятная навигация, быстрые действия.
